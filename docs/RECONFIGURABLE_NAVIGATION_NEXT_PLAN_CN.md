## 1. 结论与下一步

当前项目已经具备在 MuJoCo 中执行 NAV、PUSH、CLIMB 并逐技能重规划的工程基础，但尚未实现原方案定义的世界模型可重构导航。

当前执行顺序：

1. 冻结并使用三份选定模型包、机器人profile和显式AVX2入口，核对最终29/32报告与代码版本。
2. 使用已接入的executor、规则支撑规划器和N1快照，保留真实成功、失败、拒绝及预算截断。本轮代表回归及十条快照重放已通过。
3. 扩展推面、接近、停放和落点的几何候选，明确动作的可执行范围，采集按场景族分组的数据；不将剩余高台失败或宽工况扫描作为前置门槛。
4. 用新技能数据建立特权状态转移、成功率、碰撞风险和代价预测基线，再让世界模型参与候选选择及逐技能重规划。VLM/RGB-D随后接入。

最新模型、录像及复现命令见 [箱体训练记录](BOX_SKILL_TRAINING_CN.md)。目前三轮候选训练均结束，生产默认actor/Oracle未替换；文档更新不代表再次训练或发布了新代码。

保留的长期路线为：

```text
迁移验收与基线固化
-> 可回放的技能级数据接口
-> 参数化场景、几何候选与 MuJoCo 物理反事实评估
-> 特权状态世界模型与离线评估
-> 世界模型驱动的闭环规划
```

“推箱形成支撑后登高台”的29/32组合结果已被用户接受，当前通过显式Box后端接入共享executor。原有失败、四足停稳和无物理reset判据保留；这不代表原生高台actor独立达标或任意布局可用。JUMP、搭桥和Sim-to-Real仍不在当前实现范围，不为动作观感重新训练已接受的actor。

新箱体流程已兼容技能边界记录和独立快照rollout。当前小样本只验证数据链路；下一项应提供真正可执行的几何候选与场景族划分，再开展世界模型训练。

## 3. 开发原则与范围

1. **保留现有基线。** 原规则规划器、技能接口、actor 和固定课程继续作为回归基线；以旁路模块和可选择后端接入数据、候选评估与学习模型，不为目录美观重构全仓库。
2. **先物理数据，后学习模型。** 不把直接修改箱体位置的演示、理想目标位姿或规则规划结果当成真实状态转移标签。
3. **先特权状态，后感知。** 世界模型首次闭环仍使用 MuJoCo 真值；RGB-D 接入时不再让推理端读取隐藏的 MJCF 几何、质量或摩擦。
4. **模块职责保持原设计。** VLM 提 WHAT；几何模块落 WHERE；世界模型判断 WHETHER；executor 只执行首个技能，安全检查有最终否决权。
5. **能力值必须有物理依据。** 当前 Capability 是配置约束，不是测出的通用能力证书。降低能力上限可以作为保守 profile；增加上限必须有对应 actor/动力学配置的实测支持，不能只改向量就声称机器人变强。
6. **失败可解释，拒绝有边界。** 区分几何不合法、物理执行失败、预算不足、状态无效和人工中断。有限候选搜索未找到解只能记为预算内未找到，不能直接证明场景物理不可达。
7. **不把所有后续任务串成前置条件。** 世界模型 MVP 不等待 JUMP、大型 VLM、任意网格理解或实机部署；高台支撑分支可以独立推进。

## 6. N1：技能级数据与可回放快照

本节保留 N1 的目标规格；当前已实现的边界、事件和快照范围以开头链接的验收记录为准，直接接入现有 [executor](../mujoco/reconfigurable_navigation/runtime/executor.py)。

### 6.1 统一记录与监督标签

建议新增可序列化的 `SkillTransition`，保留现有 `SkillExecutionRecord` 兼容性。每条记录至少包括：

```text
schema_version, episode_id, scene_family_id, snapshot_id, candidate_id
scene_seed, rollout_seed, capability_profile_id
code_commit, policy_hashes, runtime_config_hash, simulator_version
observation_before, action, observation_after
previous_skill, controller_context, elapsed_sim_time, control_steps
executed, outcome, failure_reason, interrupted, truncated
labels, label_validity_mask, candidate_source, oracle_budget
```

标签覆盖原方案的 `next_robot_state`、对象状态变化、`skill_success`、`collision`、`support_stable`、`terminal`、`task_success`、`reachability` 和 `execution_cost`，但不强迫每条样本都提供所有标签：

- `terminal` 表示 episode 结束，不等于任务成功；超时和用户中断不能混为物理失败。
- `can_execute=False` 的请求记为未执行，不能伪造一次零位移的动力学样本；动力学损失使用 executed/valid mask。
- 碰撞标签来自真实接触，并区分允许的脚底支撑、允许的末端推动和非法机身/腿部接触。
- 代价包含接近、技能切换准备、执行和退出时间，不能遗漏 CLIMB 前的 `0.5 s` 准备阶段。
- 支撑稳定性需要接触关系、支撑面和持续稳定窗口；首版没有足够判据时将标签置为 unknown，不使用“base 没倒”替代完整支撑稳定标签。
- 路径几何可达、物理后续任务成功是两个不同标签。reachability 使用实际成功后缀或带预算说明的 Oracle 结果；未找到后缀时保留 unknown/预算耗尽状态。

首版采用 JSONL 元数据和分片的压缩 NumPy 数组即可，避免立刻引入数据平台。对象数组使用明确 dtype、padding、mask 和稳定 ID 映射，避免依赖 Python object pickle；并行 worker 写独立 shard，再合并 manifest。

### 6.2 编码和信息边界

- 保留原计划的 `8x128x128` BEV、`32x16` Object Tokens、12 维 Robot State、4 维 Goal 和 8 维 Capability 作为兼容基线，不假定现有 dataclass 已经实现这些张量编码。
- 冻结世界/机器人/BEV 坐标系、米/秒/弧度单位，以及 yaw、目标支撑面高度、机器人 base 高度之间的转换；原始物理值与归一化张量分开存储。
- 明确对象类别枚举映射、32 对象的筛选/溢出策略、padding mask、对象指针及 support pointer；有效标记和置信度分别保存，不能默默用同一个数表达两件事。
- 原始 token 不含对象 yaw/速度；Robot State 也不含关节状态和机械臂姿态。raw record 保留这些信息，先通过对照实验判断其对预测的影响，再决定辅助特征或显式 schema v2，不能无版本地扩维或丢失关键状态。
- 完整快照用于物理复现，不自动成为模型输入。未来 RGB-D 模式不可直接读取不可感知的质量、摩擦、真值类别和实例 ID；特权模型应明确标注其输入权限。
- 优先在清晰的技能决策边界采样，并记录上一个技能及控制上下文。若控制器历史导致同一观测下结果差异明显，应补充可获得的上下文或建模不确定性，不把回放缺陷当成动力学随机性。

### 6.3 快照与恢复

反事实实验必须在独立 rollout 实例中恢复同一快照，不能在正在执行真实任务的 `MjData` 上试动作再假装没有发生。

快照范围至少包括：

- 场景生成参数、随机化后的 model 参数及所有随机数状态。
- MuJoCo 完整的相关 integration state，例如时间、qpos/qvel、act、ctrl、外力、mocap、userdata 和 warm-start；优先使用 MuJoCo state API，并检查本模型额外需要保存的字段。
- locomotion history/last action、CLIMB target history/last action/delay profile，以及当前 actor、技能阶段、预算计数等执行上下文。
- 被外部代码维护、无法仅从物理状态重建的观测和控制缓存；可重建的接触/传感器量应在恢复后按一致顺序重新计算。

技能切换不 reset 的现有约束继续适用于真实 episode；离线分支的 snapshot restore 是另一种操作，必须分开计数和记录。

### 验收门槛

- 同一主机、同一版本、同一快照和动作至少重复 3 次，状态轨迹和结果在预先登记的容差内复现。
- 改变候选评估顺序不改变各候选结果，也不污染主 episode；保存后读取的记录与原记录字段一致。
- 开启记录器前后的固定课程结果不变，存储开销可测且有上限。
- 先采集约 500-1000 条 pilot transition，实际覆盖成功、执行失败、超时和中断；缺失样本类型需主动构造，不能为了比例伪造标签。
- 单条记录能回放原动作并定位失败时刻。未达到此门槛，不扩大到十万级数据采集。

## 7. N2：参数化场景、候选与物理 Oracle

### 7.1 参数化场景和能力标定

第一批仍以 Blocked Passage 为主，固定复杂课程作为兼容回归；不要同时扩展到任意房间和搭桥。

- 参数化机器人起点/朝向、箱体位置/尺寸/偏航、通道宽度、目标点，以及质量和摩擦。
- 先在旧基线附近做单变量扫描，再组合随机化。把高摩擦、极限尺寸和不可推动对象作为明确的边界/负样本分组，不要求既有 PUSH 对所有设置都成功。
- 按原计划组织约 `25% 直接可达 / 50% 需要重构 / 25% 不可行` 场景。第三类应由可检查的几何/能力条件构造，不能用一次搜索失败代替不可行证明。
- 建立实测 capability profiles：允许技能、可验证的推物/台阶范围、actor 和动力学配置。保守 profile 只能收紧已测范围；更大能力需要新证据。
- 相同基础场景配不同能力 profile，检验候选与拒绝结果是否合理；同时保存几何可行性和真实执行结果，避免只学到手写阈值。

### 7.2 模板提案与几何 grounding

[当前 OraclePlanner](../mujoco/reconfigurable_navigation/oracle_planner.py) 继续作为规则 baseline，另外实现候选生成和 grounding 接口：

- 为阻挡对象提出若干可达推面、退出区域和 PUSH target，替代复杂场景中唯一的固定 push_target。
- 首先处理盒状物体和已知平面；从真值几何计算自由空间、接近位姿、推向、路径扫掠和最终停放空间。
- CLIMB 入口先对简单台阶/平台自动计算候选并校验，保留现有人工 portal 作回归对照；任意三角网格 portal 提取推迟到输入几何可靠之后。
- 用 footprint、能力上限、对象有效性和支撑余量过滤候选。几何过滤仅判断必要条件，不能宣称动作一定物理成功。
- 保留候选来源与拒绝理由；先枚举少量离散参数，再接 CEM，不让连续优化在无边界空间搜索。

### 7.3 新增物理候选 Oracle

为每个候选恢复 N1 的快照，使用同一套 runtime 和 Skill API 实际执行技能；记录真实位移、接触、稳定性、代价及后续可达性。分支预算、技能深度和后缀策略显式配置。

必须区分三种结果：

| 名称 | 用途 | 不能声称 |
| --- | --- | --- |
| 现有规则 Oracle | 可复现的工程 baseline、候选来源之一 | 已验证所有连续动作的物理结果 |
| MuJoCo 候选 rollout Oracle | 数据教师、同预算候选下的物理参考 | 全局最优解或所有不可达情形的证明 |
| 学习世界模型 | 近似预测和快速候选评估 | 替代碰撞/能力等硬约束 |

### 验收门槛

- 同一场景至少出现多个具有不同真实结果/代价的候选；候选次序和真实 episode 互不影响。
- 反事实候选在独立物理 rollout 中产生标签，不调用运动学 `set_box_pose()` 生成执行结果。
- 在随机位置/朝向下可自动产生并验证 PUSH 参数，保留固定目标 baseline 进行比较。
- 发布数据集 v1，建议先达到约 1-3 万条有效执行 transition；按失败/边界覆盖和验证曲线决定是否扩容。
- 数据按 scene family 分组划分 train/validation/test，例如 70/15/15；同一基础场景的反事实、能力变体和相邻帧必须在同一 split，禁止泄漏。

## 8. N3：特权状态世界模型

### 实现顺序

1. 先建立静态/运动学预测及小型 MLP 基线，确认标签、单位和评估脚本有效。
2. 实现 BEV CNN、对象 token 编码、Robot/Goal/Capability/Action 编码，保留对象级信息，不提前做整体均值池化。
3. 按原方案实现小规模 Transformer dynamics，先预测一步，再评估 3-5 技能 rollout；初期不做像素或视频生成。
4. 首批训练 3 个独立初始化/重采样模型组成 ensemble，资源和收益足够时再扩展到 5 个。
5. 训练状态增量、技能成功、碰撞、支撑、终态、可达/价值和代价头；未观察到或未定义的标签使用 mask，不把 unknown 当成 0。
6. 在 validation 集进行概率校准和规划阈值选择，test 集只用于最终评估。关注 ensemble 分歧的局限，不能把低分歧等同于分布内安全。

### 初版验收建议

- 按技能/成功失败/边界分别报告机器人和对象终点位置、yaw 误差及 P95，不只给混合平均 loss。
- PUSH 成功样本的对象终点平移 MAE 可先以 `<=0.05 m`、yaw MAE `<=10 度` 为目标；最终容差应由通道余量与 pilot 误差决定，并在正式测试前固定。
- Success AUROC 建议 `>=0.85`，ECE 建议 `<=0.10`，Brier Score 优于按训练先验给常数概率的基线；同时报告分层可靠性图。
- 稀有碰撞事件增加 PR-AUC、漏报率和带置信区间的样本数量；ROC-AUC 单项通过不能作为安全门槛。
- 多步 rollout 在相同动作序列上与物理 Oracle 比较；若一步尚不可靠，不增加规划深度。
- 最关键是候选决策质量：比较真实最优候选与模型选择的实际成功率/代价差，而不仅是预测误差。

模型应保存 schema、训练 split、能力范围、策略 hash 和归一化参数。更换低层 actor、延迟语义或场景动力学后，原模型数据不自动有效。

首版模型优先覆盖 Blocked Passage 的 NAV/PUSH 转移；CLIMB 先保留为执行回归，再按数据覆盖逐步纳入。每个模型版本声明支持的技能、场景和能力范围，未覆盖的技能不得交给该模型评分后直接执行。低层 actor 能执行 CLIMB，不代表世界模型已经能够可靠预测 CLIMB。

## 9. N4：世界模型闭环规划 MVP

### 规划与执行

- 接入“模板候选 → grounding → 技能图搜索 → CEM → 模型 rollout/评分”，保留原规划后端可切换。
- 先验证单次 PUSH 与后续 NAV，再扩大到 3-5 技能搜索。CEM 只优化已通过对象/支撑指针校验的连续参数，并保持可行域约束。
- 初始预算可设为 3-10 个骨架、每轮 32 个参数样本、4 轮 CEM；这只是待 profiling 的起点，需报告候选数、墙钟耗时、模型调用和峰值显存。
- 评分包含任务/可达概率、碰撞、支撑风险、执行代价及 ensemble 不确定度；硬安全约束不能靠加分抵消。
- 继续只执行首个技能。每次结束后对比预测与真实状态，超过已标定阈值则废弃旧预测后缀、重新观测并生成新候选。
- 模型不可用、超时、OOD 或没有可行动作时，使用预先定义的重新观测/保守模板/安全保持或拒绝流程；不能无条件回退到一个未经物理验证的动作。
- 在切换准备和技能执行期间检查安全与中断，确保预算耗尽后的行为有明确终态；真正的跌倒恢复策略仍是后续单独训练项。

### 两步上线

1. **Shadow mode**：仍由规则 baseline 控制真实执行，模型旁路预测/排序，测量误差、候选差异和耗时。
2. **闭环 mode**：只有 shadow 数据和离线门槛通过后才由模型选择动作；保留回退原因和预测-执行对照记录。

### 验收门槛

- 在独立测试集上达到第 13 节的原始 MVP 底线，并且所有固定基线回归保持通过。
- 相同场景、同一低层策略、同一候选/时间预算下，与规则 baseline 和物理候选 Oracle 公平比较。
- 当规则 baseline 已接近满分时，不声称模型必须提高成功率；可以证明在可比成功率下减少在线物理 rollout、降低候选评估成本或扩展可处理参数范围。
- 展示至少一次模型区分多个候选、一次动作偏差后重规划、一次不安全/不可行请求被拒绝的完整可回放记录。
- 若模型评分不影响决策，或者仍由固定目标规则决定所有动作，不能宣称完成“世界模型规划”。

## 10. N5：VLM Proposal 接入

VLM 不是近期数据采集的依赖。N4 已能靠模板跑通后，再检验语义提案是否增加有价值的候选。

- 输入受控场景摘要、对象关系、能力和目标，输出少量结构化技能骨架；不输出关节动作，也不直接决定力矩、落点安全或推力。
- 严格校验 schema、技能白名单、对象/支撑指针、参数范围和最大深度；当前不可执行的 JUMP/PLACE 必须拒绝。
- 对非法 JSON、无效对象、超时、服务不可用和重复候选设置模板回退，整个系统不得依赖 VLM 永久在线。
- 模型输入不含测试结果、未来状态、Oracle 最优动作或隐藏物理标签。记录模型/提示词版本、延迟和调用成本，不记录 API 密钥。
- 使用相同 grounding、world model 和 executor，对比模板与 VLM 的有效候选率、覆盖率、任务表现及成本。

验收要求：无效提案不会到达执行器；强制断开 VLM 仍能运行模板闭环；收益以候选与任务指标证明，不用文字解释质量代替任务结果。

## 11. N6：从真值到 RGB-D 的输入替换

先保持低层技能和 N4 规划器不变，按以下顺序替换：

1. MuJoCo 4-6 个固定相机输出 RGB、Depth、标定和监督用实例标签，建立可重现数据采集。
2. 深度反投影/多视角融合，构建带已观测 mask 的 8 通道 BEV；未观测区域不默认是自由空间。
3. 检测/重建对象并跨技能关联稳定 ID，生成估计的几何、语义、置信度和候选入口。
4. 对遮挡、深度噪声、标定误差、漏检、误分类和 ID 切换做分层测试。
5. 逐层替换真值几何和对象输入，测量每一层造成的任务成功率下降；必要时用估计输入重新训练或校准世界模型。

必须先解决 BEV `6.4 m x 6.4 m` 的坐标和覆盖策略：固定全局图、机器人中心局部图及图外目标的高层表示需要明确，不能因为目标落在栅格外就伪造可达性。

验收要求：推理输入的数据血缘可检查；GT 实例 ID 只用于监督/评测，不用于线上对象关联；精确 MJCF、质量和摩擦不偷渡到视觉推理路径。至少报告真值版和视觉版在同一测试集的结果、几何误差、ID 稳定性和未知区域处理结果。新相机与域外场景应作为独立测试，不能与训练帧随机混分。

## 12. N7：真正的 High Platform Access

这是对原 P7 的补完，而不是把当前低台阶演示换一个名字。

目标任务：

```text
目标高台无法直接攀爬
-> 选择可移动且能稳定承载机器人的箱体
-> PUSH 到高台前合适位置
-> 退出接触并确认箱体位置与支撑稳定
-> CLIMB 到箱体
-> CLIMB 到高台
-> NAV 到最终目标
```

### 关键工作

- 场景必须排除绕路和直接爬台阶的替代路径，让中间支撑物成为必要条件。
- 建立支撑面图，以当前支撑面到下一支撑面的相对高度差判定可爬边，不能将第二级平台的绝对高度直接与 max_step_height 比较。
- 将支撑对象状态纳入落点与稳定性检查，明确足部安全区域、机器人尺寸余量、滑移/倾覆和成功保持时长。
- 现有低摩擦脚轮箱只证明可推动，不自动证明可承载 CLIMB。不能通过推完后冻结箱体、突然提高摩擦或直接改位姿伪造支撑；若设计刹车/锁止机制，必须显式建模为可执行操作并记录成本。
- 先测试当前 actor 对箱体上落稳和二次起步的适用范围。只有实测证明确实超出技能覆盖，才扩展 CLIMB 训练分布并重新做 Isaac/MuJoCo 对齐。
- 新场景、新 actor 或新支撑模式的数据单独版本化，补齐 support_stable 标签并重新评估模型，不能直接混用旧台阶标签。

验收分两档：固定场景连续 20 次物理通过；再使用独立参数化测试集报告推箱成功、支撑稳定、两次 CLIMB 成功、最终到达与错误拒绝。能力减弱时应出现不同可行方案或明确拒绝，不能只修改 Capability 文本而保持相同物理能力。

## 13. 统一评测与阶段退出标准

### 测试分层

| 测试集 | 目的 | 规则 |
| --- | --- | --- |
| Golden regression | 防止破坏已经可用的技能 | 保留当前固定课程、动作和验收语义 |
| IID held-out | 衡量同分布泛化 | 按场景族划分；与训练、调参隔离 |
| 边界/OOD | 暴露质量、摩擦、尺寸、能力和布局边界 | 单独报告，不与简单场景混成总分 |
| 故障注入 | 验证闭环和安全终态 | 接触丢失、超时、状态无效、预算耗尽、VLM 不可用及感知 ID 变化 |

首版建议至少 200 个冻结的 held-out 场景，保留原 25/50/25 分层，并对所有方法使用相同初态和种子。报告样本数及置信区间，不能用当前 10 个固定课程成功代替泛化评估。

### 保留原方案的 MVP 底线

| 指标 | 原方案门槛 |
| --- | --- |
| NAV 成功率 | >=95% |
| PUSH 技能成功率 | >=85% |
| Blocked Passage 任务成功率 | >=80% |
| 非法碰撞率 | <=10% |
| 已证实不可行场景的正确拒绝率 | >=85% |

同时报告重构后路径可达率、错误拒绝可行任务的比例、平均重规划次数、规划/执行时间、状态预测误差、AUROC/Brier/ECE、候选选择代价差与 Capability 方案变化正确率。场景采样混合权重不能掩盖某个分层完全失败。

这些比例是仿真研究 MVP 底线，不是实机安全标准，也不能用来放宽当前 golden regression 的零非法接触要求。CLIMB/高台任务新增门槛在对应阶段定义，不能冒用 PUSH 指标。

### 必做 baseline 和消融

保留原方案六组方法：仅导航、规则重构、VLM 不经世界模型评分、世界模型+模板、VLM+世界模型、同预算 MuJoCo rollout Oracle。所有方法共享相同可执行技能与硬安全检查；没有世界模型不意味着绕过安全约束。

按阶段补齐：去掉 Capability/Object Tokens/BEV、去掉 ensemble、固定参数对比 CEM、开环对比逐技能重规划、真值输入对比 RGB-D。比较不可达拒绝时只使用有充分依据的负标签，预算耗尽单独统计。

## 15. 双 4090 服务器资源安排

- MuJoCo 数据生成主要消耗 CPU 和主机内存，不会因安装两张 4090 自动变成 GPU 物理仿真。先 benchmark 单 worker，再增加独立进程；限制每个 worker 的 PyTorch/BLAS 线程，避免过量线程争抢。
- GPU 0/1 优先各训练一个 world-model ensemble 成员或不同 seed，第三个成员排队。小模型初期无需 DDP；DDP 是 profiling 后的可选优化。
- 世界模型训练建议使用独立轻量 CUDA PyTorch 环境，与已冻结 Isaac 技能训练环境隔离，避免额外 ML 依赖破坏已知仿真栈。
- 不同时运行满负载技能训练、两个 ensemble 作业和大规模录像；按 CPU、显存、RAM 和磁盘实测吞吐限流。
- 记录数据生成速率、有效 transition 比例、GPU 训练吞吐和评测耗时；数据扩容以学习曲线和错误覆盖为依据，不以占满显卡为目标。

| 第 3 天 | 实现物理/控制器快照恢复，独立 rollout 单个技能 | 同快照重复性、候选顺序独立性测试 |
| 第 4 天 | 围绕已验证箱体设置生成小范围参数化场景及多个 PUSH 候选 | 自动 grounding 样例、真实分支结果差异 |
| 第 5 天 | 汇总 pilot 数据、回放失败案例、固定场景族 split | 500-1000 条有效记录或明确瓶颈报告，决定是否扩容 |

第一周不以“已经开始训练 Transformer”为成功标准；以数据能复现、标签可信、失败可解释、反事实不污染主执行为退出标准。

## 17. 暂不推进的事项

- 不为让 CLIMB 动作更平滑而重训，不修改已对齐的观测、PD 和延迟语义作为无依据的优化。
- 不把现有多技能固定演示的重复成功当作世界模型或视觉泛化成功。
- 不在数据/物理 Oracle 尚未成立时训练大型视频世界模型或用 VLM 直接输出低层动作。
- JUMP、Gap Repair、长物体搭桥、完整跌倒恢复和 Sim-to-Real 在相应前置验收后另立任务；不因为枚举里有名字就允许 planner 调用。

最终推进依据是：每增加一个模块，都能通过独立输入/输出、版本化数据和同预算对照实验证明它解决了当前系统的一个明确缺口。
